# Developer guide: contributing

The root `CONTRIBUTING.md` covers setup, gates and community expectations. This
guide covers the internal contracts you need to change code safely.

## Layering

```text
api/routes  ->  services  ->  database / workflow / chemistry
cli/main    ->  services  ->  database / workflow / chemistry
```

- Routes validate HTTP payloads and translate service exceptions. They do not
  contain business logic.
- Services own transactions, validation and audit events.
- Workflow nodes own scientific computation and declare their columns.
- The CLI calls the same services. A UI action without a CLI path is a parity
  bug.

When adding a feature, implement the service first, then the API, then the CLI,
then the UI. Add tests at the service and API layers before the UI.

## Adding an API route

1. Add or extend a Pydantic request/response model in `api/schemas.py`.
2. Add the route in `api/routes/<domain>.py`.
3. Use `Depends(db)` for the session and `request.app.state.registry` for the
   node registry.
4. Raise `AppError` subclasses for expected failures; the global handler maps
   them to the `{error: {code, message, details}}` envelope.
5. Add an integration test in `tests/integration/test_api.py`.
6. Add the CLI equivalent and a CLI test.
7. Update `docs/user-guide/CLI.md` and the OpenAPI-visible description.

## Adding a CLI command

- Register it on the appropriate Typer sub-app in `cli/main.py`.
- Use `_run_cli` to translate `AppError` into the stable exit code.
- Use `_print` so `--json` works consistently.
- Destructive commands take `--yes` and otherwise confirm.
- Add a test that exercises both human and `--json` output.

## Adding a workflow node

See `docs/architecture/PLUGIN_API.md` for the full contract. In short:

1. Add a Pydantic config model with bounded fields.
2. Implement a pure handler that returns a new `Table`.
3. Declare every output `Column` with method, unit and direction.
4. Register it in `register_builtin_nodes`.
5. Add unit tests for normal, missing-value and invalid-config cases.
6. Add a cache-key test if the node is expensive.
7. Update `docs/user-guide/WORKFLOWS.md`.
8. Decide whether the node is safe for the demo; if it needs weights or a
   network, do not register it as runnable.

## Database changes

Alembic is the schema authority.

```bash
uv run alembic revision --autogenerate -m "add table"
uv run alembic upgrade head
uv run hcs-discovery db current
```

- Review autogenerated migrations by hand.
- Keep `migrations/versions` in the wheel/sdist story in mind: the application
  falls back to `create_all` only when migration assets are absent.
- Add a migration test in `tests/integration/test_migrations.py`.
- Never edit a released migration; add a new revision.
- Back up `data/hcs.sqlite3` before testing a migration on real data.

## Frontend changes

- Server state goes through TanStack Query in `api/queries.ts`.
- Add types in `api/types.ts`; do not use `any` for API payloads.
- Use the existing UI primitives in `components/ui.tsx`.
- Use design tokens from `styles/global.css`. Check light, dark and narrow
  layouts.
- Every action must show a loading state, a success/failure toast, and a
  recoverable error state.
- Do not display a feature that the API cannot perform. If it is planned, label
  it as planned and make it non-interactive.
- Add or extend a Playwright test for a user-visible flow.

## API/CLI/UI parity checklist

For each user action, verify:

- [ ] API endpoint exists and is documented.
- [ ] CLI command exists with `--json`.
- [ ] UI calls the API and handles errors.
- [ ] Authorization and network policy are enforced in the service/API, not
      only in the UI.
- [ ] The action is audited if it mutates data.
- [ ] Docs list the command and endpoint.
- [ ] A test covers the failure path, not only the happy path.

## Error handling

- Expected user errors use `ValidationError`, `NotFoundError`, `ConflictError`,
  `PolicyError`, `MissingDependencyError` or `RunCancelledError`.
- Unexpected exceptions are logged with a redacted traceback and returned as
  `internal_error`; never leak a stack trace to the browser.
- Messages must not contain secrets, absolute paths with user names, or raw
  provider responses.

## Security review triggers

Request a security review for changes involving:

- authentication, tokens, CORS or bind addresses,
- file upload, archive extraction or path handling,
- HTML/Markdown rendering,
- subprocess execution or external binaries,
- network clients or provider credentials,
- dependency additions with install scripts.

## Release hygiene

- Update `CHANGELOG.md` and `docs/engineering/IMPLEMENTATION_STATUS.md`.
- Re-run every gate in `TESTING.md`.
- Regenerate screenshots only from the running application.
- Build the wheel and smoke-test it.
- Do not tag a release from a dirty working tree.
